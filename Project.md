Below is a **master build specification** designed to be pasted into another coding-capable LLM such as Claude, Gemini, ChatGPT/Codex, Cursor, or another AI development agent.

I have written it as a **software requirements + implementation specification**, rather than a normal college synopsis. The goal is that another LLM can use this document to actually build the application.

One important design decision: the application must use **synthetic/fictitious voter data only**. The 25,000 voter records should be generated by code with a fixed random seed so the dataset is reproducible. The system must never claim that the synthetic data represents real voters or real election records.

# 2. IMPORTANT PROJECT SAFETY AND SCOPE RULE

This is an **academic simulation**.

The application must use:

> **100% synthetic/fictitious voter information.**

Never use:

* real voter IDs;
* real Aadhaar numbers;
* real government IDs;
* real addresses;
* real phone numbers;
* real election databases;
* real electoral-roll information;
* real biometric information.

The application must clearly display:

> **DEMO / ACADEMIC SIMULATION — ALL VOTER DATA IS SYNTHETIC**

The LLM must never make a legally authoritative decision about whether a real person is eligible to vote.

The AI provides **information and workflow assistance only**.

---

# 3. PROJECT OBJECTIVE

Build a complete web application in which a simulated polling officer can:

1. Search synthetic voter records.
2. Check whether a synthetic voter has already been processed.
3. View the voter's simulated details.
4. Ask questions about voter records using natural language.
5. Ask questions about polling-station statistics.
6. Ask questions about procedures using RAG.
7. Detect anomalous records using machine learning.
8. View election-processing analytics.
9. Ask the LLM to analyse the data.
10. Generate charts and reports.
11. View an audit trail of system/AI activity.
12. Interact with all of these capabilities through one conversational interface.

# 16. CONTROLLED DUPLICATES AND ANOMALIES

The user specifically wants duplicate dummy data.

Implement two different concepts.

### A. Duplicate-looking records

Create a controlled subset of synthetic duplicate/inconsistent records for testing.

For example:

```text
5% of generated events
```

can contain controlled data-quality issues.

But the primary `voter_id` must remain unique.

### B. Anomalous processing events

Introduce:

* duplicate processing events;
* unusually short processing time;
* unusually long processing time;
* excessive station activity;
* inconsistent timestamps;
* missing station assignment;
* repeated processing;
* abnormal queue time.

These anomalies will be detected by the ML module.

# 76. One Important Recommendation About the 25,000 Records

I **do not recommend putting 25,000 individual voter records directly into the LLM prompt/documentation**.

Instead, the application should contain:

```text
generate_dataset.py
        ↓
25,000 records
        ↓
voters.csv
        ↓
PostgreSQL
        ↓
LLM tools
```

This is much better technically.

The LLM building the application can generate the **generator program**, which will automatically produce the 25,000 records. This gives you:

* exactly 25,000 records;
* reproducibility;
* no accidental duplicates;
* controllable distributions;
* controllable anomalies;
* easier testing;
* much smaller project files;
* the ability to regenerate the dataset whenever required.

You can use **seed = 42** so that every student on the team gets the same dataset.
